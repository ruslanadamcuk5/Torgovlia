# Релизы и обновления

Процесс рассчитан на модульный монолит и небольшой сервер: один артефакт
(frontend `dist` + backend), одна миграция Alembic, быстрый откат.

## 1. Ветки и версии

- `platform` — рабочая ветка платформы; `main` и `rybnaya-lavka` не трогаем.
- Изменения — через отдельную ветку и PR в `platform`.
- Версия отображается в `/api/health` как `version` (`1.0.0`).
- В журнале релиза указывается коммит, дата, окружение и кто проверял.

SemVer для платформы:

- `major` — несовместимые изменения API/данных;
- `minor` — новая функциональность;
- `patch` — исправления и тексты.

## 2. Перед релизом

- [ ] Задача/PR прошли ревью, нет секретов в диффе.
- [ ] `pytest -q` — зелёный (включая `test_isolation.py`, `test_monitoring.py`).
- [ ] `cd frontend && npx tsc --noEmit`.
- [ ] `npm run build` с `VITE_*` целевого окружения.
- [ ] Миграция проверена на чистой БД:
      `DATABASE_URL=sqlite:////tmp/mig.db alembic upgrade head`, затем
      `downgrade -1` и повторный `upgrade head`.
- [ ] Миграция проверена на копии боевой базы/staging.
- [ ] Сделан свежий бэкап (`deploy/backup.sh`) и проверен `--verify-only`.
- [ ] Обновлены `docs/platform/PLAN.md` (журнал) и пользовательская
      документация, если изменилось поведение.
- [ ] Демо-пароли и токены не попали в релиз.

## 3. Правила миграций

- Только аддитивные изменения: новые таблицы/колонки/индексы.
- Удаление и переименование — в два релиза: сначала новое поле и двойная
  запись, потом удаление старого.
- Новые колонки — с `nullable` или `server_default`; иначе миграция упадёт на
  непустой таблице.
- `downgrade()` обязателен и проверен, если откат возможен.
- Долгие операции на большой таблице — отдельным релизом/окном.
- Одна голова Alembic: `alembic heads` должен вернуть одну ревизию.

## 4. Staging

1. Развернуть/обновить отдельный стенд по `docs/STAGING.md`.
2. Применить миграции на копии боевой базы.
3. Прогнать `scripts/smoke.py --full`.
4. Проверить вручную: вход владельца, заказ, смена статуса, сертификат,
   регулярный заказ, задачи, CRM, рассылка (в демо-режиме), панель платформы.
5. Проверить, что `DEMO_MODE=false`, `TENANT_HEADER_ENABLED=false`, SMS не
   боевой, `DEBUG=false`.

## 5. Деплой

### alwaysdata

```bash
cd /root/workspace/torgovlia
ALWAYSDATA_TOKEN='<токен>' python3 deploy/alwaysdata/deploy.py \
  --account torg --skip-build --skip-install --wait 180
python3 scripts/smoke.py --base-url https://torg.alwaysdata.net \
  --demo --tenant odezhda --full
```

`start.sh` применяет `alembic upgrade head` при старте. После деплоя проверить
`/api/health`, витрину, админку, `/platform/ops` и лог сайта.

### Собственный сервер / hoster.by

```bash
./deploy/backup.sh
git pull
docker compose up -d --build
curl -fsS https://<домен>/api/health
```

Если миграции не применяются автоматически — `cd backend && alembic upgrade head`
до перезапуска приложения. Сначала обновляем staging, потом production.

## 6. После релиза

- [ ] `/api/health` — `ok`.
- [ ] `scripts/smoke.py` — зелёный.
- [ ] Вход владельца и покупателя.
- [ ] Создание и выдача тестового заказа (на демо/тестовом магазине).
- [ ] Логи без новых `ERROR`/`Traceback`.
- [ ] Проверить `/platform/ops`: нет новых красных статусов.
- [ ] Записать релиз в журнал.

При ошибке — не «чинить на живом»: откатить код/базу и разбираться на staging.

## 7. Откат

1. **Код**: вернуть предыдущий коммит и задеплоить его.
2. **Миграция**: `alembic downgrade -1`, только если `downgrade()` проверен и
   нет потери данных. Иначе — восстановление базы из копии.
3. **База**: остановить приложение, `deploy/restore.sh --db ... --yes`,
   запустить, проверить health и smoke. Текущая база сохраняется с суффиксом
   `.pre-restore-*`.
4. **Медиа**: восстановить `media-*.tar.gz` при необходимости.
5. Записать причину отката и результат в журнал инцидентов.

## 8. Горячее исправление

- Ветка `hotfix/<короткое-имя>` от `platform`.
- Минимальный диф, только исправление; без рефакторинга.
- Те же проверки, что и для обычного релиза, но можно сократить ручной набор
  до затронутого сценария + smoke.
- После деплоя — сообщение арендаторам, если их затронуло.
- Постмортем, если инцидент был `major`/`critical`.

## 9. Заморозка

- За 24 часа до пилота/маркетинговой акции — только hotfix.
- В пятницу после 16:00 и в дни выплат — только critical hotfix.
- Во время инцидента деплой запрещён, пока инцидент не закрыт.
