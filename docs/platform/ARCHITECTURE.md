# Архитектура платформы

Статус: проект решения (ADR-001…ADR-012). Документ описывает целевую архитектуру
универсальной multi-tenant платформы и путь миграции от текущего single-tenant
приложения.

## 1. Контекст

Сейчас приложение обслуживает один магазин:

- одна глобальная запись настроек `SiteSetting(id=1)`;
- таблицы `categories`, `products`, `orders`, `users` без привязки к магазину;
- один набор маршрутов `/api`, один фронтенд, одна админка;
- SQLite в разработке, PostgreSQL в production;
- SMS, QR, заказы, каталог, настройки уже реализованы.

Нужно обслуживать неограниченное число магазинов, продавать им подписки, включать
и выключать сервисы, выдавать домены и размещение, следить за работоспособностью.

## 2. Решение верхнего уровня (ADR-001)

**Модульный монолит с логической multi-tenancy.**

- Один backend (FastAPI), одна PostgreSQL, один набор фоновых задач.
- Все бизнес-данные арендатора содержат `tenant_id`.
- Один экземпляр приложения обслуживает все сайты; маршрутизация по домену.
- Центральная панель платформы — часть того же приложения, отдельный префикс
  `/api/platform` и отдельный UI-раздел `/platform`.
- При необходимости крупному арендатору можно выдать **выделенный экземпляр**
  (premium), не меняя код: тот же образ, отдельная БД.

Почему не микросервисы на старте:

- команда маленькая, нагрузка умеренная;
- транзакции и биллинг проще в одной БД;
- меньше инфраструктуры и стоимости;
- модульные границы всё равно соблюдаются на уровне пакетов и сервисов.

Микросервисы или выделенные воркеры можно выделить позже по узким местам
(например, рассылки, импорт прайсов, AI-обработка).

## 3. Топология

```
                       ┌──────────────────────────────┐
                       │  Edge: nginx / Traefik       │
                       │  TLS, wildcard, custom hosts │
                       └──────────────┬───────────────┘
                                      │
                    ┌─────────────────┴─────────────────┐
                    │                                   │
          platform.tld / app.tld              *.platform.tld / custom domain
                    │                                   │
                    ▼                                   ▼
        ┌───────────────────────┐           ┌───────────────────────┐
        │  FastAPI (platform)   │           │  FastAPI (tenant)     │
        │  /api/platform/*      │           │  /api/*               │
        │  биллинг, провижининг │           │  каталог, заказы      │
        └───────────┬───────────┘           └───────────┬───────────┘
                    │                                   │
                    └─────────────────┬─────────────────┘
                                      ▼
                     ┌─────────────────────────────────┐
                     │ PostgreSQL (shared schema)      │
                     │ + Redis (cache, queue, locks)   │
                     │ + S3 / media storage            │
                     └─────────────────────────────────┘
                                      │
                                      ▼
                     ┌─────────────────────────────────┐
                     │ Worker: jobs, mailings, imports │
                     │ monitoring, provisioning        │
                     └─────────────────────────────────┘
```

Компоненты:

| Компонент | Назначение |
|---|---|
| `api` | HTTP API, рендер SPA, авторизация, бизнес-логика |
| `worker` | фоновые задачи: рассылки, импорт, деплой, health-checks, биллинг |
| `db` | PostgreSQL, общая схема, `tenant_id` |
| `redis` | кэш домён→арендатор, очередь задач, блокировки, rate limit |
| `s3` | изображения и файлы арендаторов (hoster S3 или локальный диск) |
| `edge` | TLS, домены, сжатие, лимиты, WAF |
| `monitor` | внешние проверки доступности и SSL |

## 4. Два фронтенда или один

Рекомендация: **один React-проект, три оболочки**.

- `/` — публичная витрина арендатора (определяется доменом);
- `/admin` — простая админка арендатора;
- `/platform` — панель владельца платформы;
- `/site` (или корень платформенного домена) — сайт продаж.

На старте это один Vite-билд с разными layout-компонентами. Если панель платформы
сильно разрастётся, её можно вынести в отдельный entry point (`platform.html`) без
разделения API.

Правила UI:

- арендатор видит крупные карточки, минимум настроек, понятные подписи;
- сложные термины (DNS, SSL, деплой) скрыты в панели платформы;
- ошибки формулируются действием: «Не удалось сохранить товар. Попробуйте ещё раз»;
- ни одна функция не требует знания API, консоли или файловой системы.

## 5. Модель tenancy (ADR-002)

### 5.1 Идентификаторы

- `tenants.id` — UUID или bigint; UUID удобнее для внешних ссылок и логов.
- `tenants.slug` — человекочитаемый адрес `slug.platform.tld`, уникален глобально.
- `tenants.status` — `draft | onboarding | active | grace | suspended | archived`.
- `tenants.plan_id`, `tenants.category_preset`, `tenants.locale`, `tenants.currency`.
- `tenants.custom_domain`, `tenants.domain_verified_at`.

### 5.2 Домены

Таблица `tenant_domains`:

| Поле | Смысл |
|---|---|
| `tenant_id` | владелец |
| `host` | `example.by`, `www.example.by`, `shop.platform.tld` |
| `kind` | `subdomain`, `custom`, `alias` |
| `is_primary` | основной адрес |
| `verified_at` | подтверждение владения |
| `ssl_status` | `none`, `pending`, `active`, `error` |
| `dns_status` | `pending`, `ok`, `error` |

Правила:

- `slug.platform.tld` создаётся сразу, бесплатно, SSL wildcard.
- Custom domain подключается через TXT-запись `_torgovlia-verify.<host>` или
  HTTP-challenge; после проверки — A/AAAA или CNAME на edge.
- `www` — алиас с редиректом на канонический хост.
- Зарезервированные slug: `www`, `api`, `app`, `platform`, `admin`, `mail`, `cdn`,
  `status`, `docs`, `support`, `billing`, `static`, `media`.

### 5.3 Резолвинг арендатора

Middleware на каждом запросе:

1. Взять `Host` (без порта), нормализовать (lowercase, punycode).
2. Проверить кэш Redis `host:<host>` → `tenant_id`.
3. При промахе: `tenant_domains` → `tenants`.
4. Если хост — платформенный, включить platform-режим.
5. Если не найден — 404 или страница «магазин не найден».
6. Для dev/test допускается заголовок `X-Tenant-Slug`, но только при
   `ENVIRONMENT != production`.

Кэш инвалидируется при изменении домена, статуса арендатора и деплое.

### 5.4 Изоляция данных

- Все бизнес-таблицы получают `tenant_id NOT NULL` и составные индексы
  `(tenant_id, ...)`.
- Уникальные ключи становятся составными: `(tenant_id, slug)`,
  `(tenant_id, phone)`, `(tenant_id, number)`.
- Базовый класс `TenantModel` и helper `tenant_query(db, tenant_id)`.
- Запись всегда проставляет `tenant_id` из контекста запроса, а не из тела запроса.
- Тест изоляции: арендатор A не может прочитать/изменить/удалить объект B ни через
  один API-маршрут. Тест запускается на каждом PR.
- Дополнительно (позже): PostgreSQL Row Level Security как второй барьер.

### 5.5 Пользователи и роли

Две независимые области идентичности:

| Область | Таблица | Кто | Область видимости |
|---|---|---|---|
| Платформа | `platform_users` | владелец SaaS, поддержка, биллинг | всё |
| Арендатор | `users` + `memberships` | владелец магазина, продавцы | один или несколько tenants |
| Покупатели | `customers` | клиенты магазина | только свой tenant |

- `platform_users`: email, пароль, 2FA, роль `owner | admin | support | billing | viewer`.
- `users`: телефон/email, пароль, профиль; `memberships(tenant_id, user_id, role)`,
  роли `owner | manager | seller | accountant`.
- `customers`: `(tenant_id, phone)` уникален; не видны другим арендаторам.
- Один человек может владеть несколькими магазинами — переключатель в кабинете.
- Импersonation: только `support`/`owner`, с записью в аудит, баннером и
  ограниченным сроком.

## 7. Реестр сервисов и entitlements (ADR-003)

Единый источник правды — код (`app/platform/services/registry.py`), синхронизируемый
в БД при старте. В БД хранятся цена, порядок, видимость и переопределения.

### 7.1 Схема сервиса

```python
Service(
    code="delivery",
    title="Доставка",
    group="Продажи",
    description="Зоны, стоимость, интервалы, курьеры",
    tier="paid",                 # free | paid | addon | platform
    price_month=Decimal("9.90"),
    dependencies=("catalog",),
    conflicts=("pickup_only",),
    default_enabled=False,
    trial_days=14,
    config_schema={...},
    icon="truck",
)
```

### 7.2 Состояния entitlement

| Статус | Значение |
|---|---|
| `enabled` | включён, доступен |
| `trial` | пробный период |
| `pending_payment` | ждёт оплаты |
| `disabled` | выключен арендатором |
| `suspended` | отключён платформой (долг, нарушение) |
| `not_available` | недоступен на текущем плане |

Правила:

- Отключение сервиса не удаляет данные, только скрывает функции и API.
- Зависимости включаются каскадно; отключение блокируется, если от сервиса
  зависят другие.
- Платформа может принудительно включить/выключить сервис
  (`locked_by_platform=true`) и задать квоту.
- Все проверки — на backend (`require_service("delivery")`), UI получает
  `features` и показывает upsell.
- Изменения entitlements пишутся в аудит.

Подробный каталог — в [`SERVICES.md`](SERVICES.md).

## 8. Биллинг и подписки (ADR-004)

### 8.1 Что продаёт платформа

- подписка на план (месяц/год);
- дополнительные сервисы (add-on);
- домен и хостинг (pass-through + наценка);
- выделенный экземпляр / SLA / white-label;
- услуги запуска и переноса.

Платёж покупателей арендатору **не проходит через платформу** на старте: арендатор
подключает свой эквайринг (bePaid/WebPay) и сам является продавцом. Это избавляет
платформу от роли marketplace и фискализации чужих продаж.

### 8.2 Жизненный цикл

```
trial → active → grace → suspended → archived
```

- `trial` 14 дней, без карты, с напоминаниями.
- `active` — оплачен период.
- `grace` 7 дней после окончания: сайт работает, в админке баннер.
- `suspended` — сайт отдаёт заглушку, админка только для оплаты.
- `archived` — данные хранятся 90 дней, затем удаление по политике.

### 8.3 Инвойсы и платежи

- `invoices`: номер, tenant, период, сумма, статус, срок.
- `invoice_items`: план, add-on, домен, хостинг, разовые услуги.
- `payments`: провайдер, внешний id, сумма, статус, идемпотентность.
- Webhook обрабатывается идемпотентно, с проверкой подписи и повторной сверкой.
- Автопродление: попытка за 3 дня, затем в день оплаты, затем grace.
- Возвраты и корректировки — через credit note.
- Сверка: ежедневный отчёт «оплачено / не оплачено / расхождения».

### 8.4 Платёжные провайдеры

| Провайдер | Назначение | Примечание |
|---|---|---|
| bePaid / WebPay | карты, ЕРИП, Apple/Google Pay | основной кандидат для Беларуси |
| ЕРИП | оплата по счёту | через банк или агрегатор |
| Банковский счёт | юрлица, ИП | ручное подтверждение |
| Stripe | не использовать | недоступен для BY-мерчантов |

Провайдер выбирается адаптером `PaymentProvider`; на старте допустим ручной режим
«выставил счёт → подтвердил оплату».

## 9. Провижининг и деплой (ADR-005)

### 9.1 Машина состояний

```
draft
  → domain_selected
  → awaiting_payment
  → paid
  → provisioning
  → dns_pending
  → ssl_pending
  → deployed
  → active
```

Ошибки: `failed_retryable`, `failed_manual`, `cancelled`. Каждый шаг идемпотентен,
имеет таймаут, число попыток и лог.

### 9.2 Задачи провижининга

| Шаг | Действие | Автоматизация |
|---|---|---|
| 1 | создать tenant + subdomain | полностью |
| 2 | засеять пресет и демо-данные | полностью |
| 3 | проверить домен (WHOIS/RDAP) | полностью |
| 4 | заказать домен | вручную / партнёрский API |
| 5 | создать хостинг-аккаунт | ispmanager API / вручную |
| 6 | задеплоить приложение | CI + SSH / API |
| 7 | настроить DNS | API регистратора / вручную |
| 8 | выпустить SSL | Let's Encrypt / ispmanager |
| 9 | health-check | полностью |
| 10 | активировать и уведомить | полностью |

### 9.3 Адаптеры

```python
class DomainProvider(Protocol):
    def check_availability(self, fqdn: str) -> DomainCheck: ...
    def register(self, req: DomainOrder) -> DomainResult: ...
    def set_dns(self, fqdn: str, records: list[DnsRecord]) -> None: ...
    def status(self, order_id: str) -> DomainStatus: ...

class HostingProvider(Protocol):
    def create_account(self, req: HostingOrder) -> HostingResult: ...
    def suspend(self, account_id: str) -> None: ...
    def resume(self, account_id: str) -> None: ...
    def delete(self, account_id: str) -> None: ...
    def stats(self, account_id: str) -> HostingStats: ...

class DeploymentProvider(Protocol):
    def deploy(self, tenant_id: str, version: str) -> DeploymentResult: ...
    def rollback(self, tenant_id: str, deployment_id: str) -> None: ...
    def health(self, tenant_id: str) -> HealthResult: ...
```

Реализации:

- `ManualDomainProvider` — создаёт задачу оператору, показывает чек-лист и ссылки.
- `HosterByPartnerProvider` — включается, если hoster.by даст API/кабинет.
- `IspManagerProvider` — управление сайтами, SSL, БД, почтой, бэкапами.
- `SshDeploymentProvider` — git pull / docker compose / systemd на VPS.

Подробности — в [`HOSTER.md`](HOSTER.md).

### 9.4 Версии и откат

- Каждый деплой фиксирует git SHA, версию образа, миграции.
- Перед миграцией — бэкап БД.
- Откат приложения — предыдущий образ; откат схемы — только вперёд
  (forward-only migrations) либо restore из бэкапа.
- Blue/green для выделенных экземпляров; для общего рантайма — rolling restart.

## 11. Безопасность (ADR-007)

- RBAC на уровне маршрутов и объектов; проверка `tenant_id` в каждом запросе.
- 2FA для платформенных администраторов; опционально для владельцев.
- Пароли — bcrypt; токены — короткоживущие + refresh; отзыв сессий.
- Rate limit по IP, tenant и пользователю (Redis).
- Загрузки: проверка MIME, размера, перекодирование изображений, антивирус позже.
- Секреты интеграций — шифрование at rest, маскирование в API и логах.
- Аудит: кто, что, когда, tenant, IP, request_id; хранится 12 месяцев.
- Импersonation — только с причиной, логом и баннером.
- CSRF: если перейдём на cookie-сессии; сейчас bearer-токены.
- Заголовки безопасности, HSTS, CSP, запрет iframe для админки.
- Регулярные проверки зависимостей и контейнеров.

### 11.1 Персональные данные (Беларусь)

Платформа обрабатывает ПД покупателей арендаторов. Требуется:

- размещение на хостинге, соответствующем требованиям Закона № 99-З и приказа
  ОАЦ № 66 (у hoster.by есть «Хостинг для персональных данных»);
- договор поручения обработки между платформой и арендатором;
- согласия покупателей, политика, сроки хранения, удаление;
- уведомление в Национальный центр защиты персональных данных (по применимости);
- журналирование доступа и инцидентов;
- трансграничная передача — только при законных основаниях.

Это **блокирующее требование для production**: до запуска выбрать
PD-совместимое размещение. Детали — в [`../COMPLIANCE-BY.md`](../COMPLIANCE-BY.md).

## 12. Наблюдаемость и мониторинг (ADR-008)

### 12.1 Метрики

- uptime и latency каждого домена (внешняя проверка раз в минуту);
- срок действия SSL (алерт за 14 дней);
- 5xx, 4xx, p95 latency по API;
- очередь задач, retry, dead-letter;
- PostgreSQL: connections, slow queries, размер БД;
- диск, память, CPU;
- SMS-баланс, ошибки платежей, ошибки провижининга;
- бизнес-метрики: регистрации, конверсия trial→paid, MRR, churn.

### 12.2 Алерты

- Telegram-канал дежурного + email.
- Пороги: сайт недоступен 2 минуты, SSL < 14 дней, 5xx > 1% за 5 минут,
  очередь > 100 задач, платёж не прошёл 3 раза.
- Инциденты фиксируются в `incidents`, статус-страница обновляется вручную или
  автоматически.

### 12.3 Логи

- Структурированный JSON: `ts`, `level`, `tenant_id`, `request_id`, `user_id`,
  `route`, `status`, `duration_ms`.
- Без ПД и секретов в логах.
- Хранение 30 дней горячих, 12 месяцев архив.

## 13. Производительность и масштабирование

- Горизонтальное масштабирование stateless API за load balancer.
- Сессии и кэш — в Redis, файлы — в S3.
- Тяжёлые операции — только в worker.
- Индексы: `tenant_id` первым в составных индексах.
- Пагинация и лимиты на всех списках.
- Кэш витрины: настройки, категории, карточки; инвалидация по tenant.
- Целевые показатели: p95 API < 300 мс, витрина < 1.5 с на 4G, uptime 99.9%.
- Нагрузочный тест: 1000 RPS на чтение, 100 одновременных арендаторов, 10k товаров.

## 14. Миграция текущего приложения

1. Добавить `tenants` и создать tenant `rybnaya` с текущими данными.
2. Добавить `tenant_id` во все таблицы (nullable → заполнить → NOT NULL).
3. Заменить глобальные уникальные ключи на составные.
4. `SiteSetting(id=1)` → `tenant_settings(tenant_id=rybnaya)`.
5. `users` разделить: staff → `users` + `memberships`, покупатели → `customers`.
6. API: получить tenant из middleware, все запросы — через `tenant_query`.
7. Фронтенд: заголовок/домен, тему и настройки брать из `/api/site`.
8. Тесты: старый сценарий «Рыбная лавка» должен проходить как tenant-тест.
9. Демо-данные: минимум 3 tenant разных категорий.

Миграции — Alembic, с проверкой на копии production-дампа.

## 15. Развёртывание

### 15.1 Варианты

| Вариант | Когда | Плюсы | Минусы |
|---|---|---|---|
| Shared на VPS/cloud | старт, до сотен арендаторов | дёшево, просто | общий ресурс, шумные соседи |
| Shared на ispmanager-хостинге | малый старт | знакомый хостинг | меньше контроля, лимиты |
| Выделенный экземпляр | premium | изоляция, SLA | дороже, сложнее деплой |
| Kubernetes | позже | масштаб | избыточно на старте |

Рекомендация: один VPS/облачный сервер у hoster.by (или PD-хостинг), Docker Compose,
nginx/Traefik, PostgreSQL, Redis, S3. Домены и часть услуг — через hoster.by.

### 15.2 Окружения

- `local` — SQLite/Postgres, console SMS, фиктивный платёжный провайдер.
- `staging` — отдельная БД, тестовые домены, sandbox платежей.
- `production` — PD-совместимое размещение, реальные ключи, бэкапы.

### 15.3 CI/CD

- Линтеры, `tsc --noEmit`, pytest, проверка миграций, сборка фронтенда.
- Docker-образ с тегом git SHA.
- Деплой staging автоматически, production — вручную или по тегу.
- Smoke-тест после деплоя: `/api/health`, вход, создание заказа.
